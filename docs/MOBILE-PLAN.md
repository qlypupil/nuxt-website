# 官网移动端适配方案建议

本文档给出「官网项目实现移动端」的方案建议，不涉及具体代码修改，仅作规划与实施参考。

---

## 一、现状简要

| 项目 | 现状                                                          |
| ---- | ------------------------------------------------------------- |
| 框架 | Nuxt 4 + Vue 3 + Tailwind CSS                                 |
| 布局 | 固定 Header + 主内容区 + 固定 Footer，主内容 `max-w-5xl` 居中 |
| 导航 | Header 内横向链接 + 语言切换，无响应式折叠                    |
| 视口 | 已配置 `viewport: width=device-width, initial-scale=1`        |
| 断点 | 未针对移动端做组件级适配                                      |

**主要问题**：小屏下导航栏横向排列会溢出或挤在一起，需要改为折叠/抽屉式导航。

---

## 二、整体策略建议

1. **先适配、再优化**  
   先保证小屏可用（导航可点、内容可读、不横向溢出），再考虑触摸体验和性能。

2. **以 Tailwind 断点为准**  
   使用 Tailwind 默认断点（`sm: 640px`、`md: 768px`、`lg: 1024px`、`xl: 1280px`），移动端以「小于 `md`」或「小于 `lg`」为基准。

3. **组件级响应式**  
   不改变现有页面路由与数据结构，仅在布局和组件上用 Tailwind 的 `md:` / `lg:` 控制显示与排版。

4. **触摸优先**  
   按钮、链接等可点击区域建议 ≥ 44×44px，避免过小或过密。

---

## 三、分项方案

### 3.1 导航栏（AppHeader）— 高优先级

**目标**：小屏下不溢出，导航和语言切换仍可用。

**建议方案**：

- **断点选择**：例如在 `< md`（768px 以下）使用「移动端样式」，≥ md 保持现有横向导航。
- **移动端形态**：
  - 左侧：Logo/站点名；右侧：**汉堡菜单按钮**（图标）。
  - 点击汉堡按钮后展开**全屏或半屏抽屉/下拉面板**，内部为：
    - 竖向排列的导航链接（首页、新闻、关于我们）；
    - 语言切换（中文 / EN）。
  - 点击链接或再次点击按钮后关闭抽屉。
- **实现方式**：
  - 用 Vue 的 `ref` 控制「抽屉是否打开」；
  - 用 Tailwind 的 `md:flex` / `md:hidden`、`hidden` / `md:block` 等切换「桌面版导航」与「移动版汉堡 + 抽屉」的显示；
  - 抽屉可用 `fixed inset-0 z-40` 全屏，或 `fixed top-14 right-0 bottom-0 w-64` 侧边栏，背景半透明遮罩便于关闭。
- **无障碍**：
  - 汉堡按钮使用 `<button>` 并加 `aria-expanded`、`aria-controls`；
  - 抽屉容器加 `id` 与 `role="dialog"` 或 `navigation`，便于读屏。

**不强制**：若产品希望移动端也保留顶部横条导航，可改为「横向滚动」或「两行排列」，但需保证文字不截断、可点区域足够大。

---

### 3.2 主内容区（default.vue 的 main）

**目标**：小屏下左右留白合理、不贴边、不横向滚动。

**建议**：

- 保持 `mx-auto max-w-5xl px-4`，仅检查 `px-4` 在小屏是否合适（一般 16px 足够）。
- 若后续有宽表格或宽图，再对**该页面**单独做：
  - `overflow-x-auto` 的容器，或
  - 在小屏隐藏/折叠部分列，仅保留关键信息。

---

### 3.3 底部（AppFooter）

**目标**：小屏下一行或两行可读，不溢出。

**建议**：

- 文案已 i18n，一般较短。
- 若将来文案变长，可考虑：
  - `text-xs` 或 `text-sm` 保持；
  - 小屏用 `flex flex-col gap-1` 或自然换行，避免单行过长。

---

### 3.4 页面内容（index / news / about）

**目标**：字体、间距在小屏舒适，无横向滚动。

**建议**：

- **标题**：当前 `text-4xl` 在大屏合适，小屏可加 `text-2xl sm:text-3xl md:text-4xl` 做阶梯缩小。
- **正文**：若后续接入富文本或长列表，建议：
  - 段落使用 `prose`（已有 @tailwindcss/typography）并限制最大宽度；
  - 列表/卡片在小屏单列，`md:` 以上再多列。
- **留白**：main 已有 `pb-16 pt-20`，避免被固定 Header/Footer 遮挡；小屏可保持或微调为 `pt-16 pb-20`，按实际点击舒适度再定。

---

### 3.5 固定定位与安全区

**目标**：固定栏不遮挡内容，且考虑刘海/底部横条。

**建议**：

- Header/Footer 已 `fixed`，主内容已有 `pt-20`、`pb-16`，逻辑正确。
- 若需兼容 iOS 刘海和底部横条，可在 `app.head` 或布局根节点加：
  - `viewport-fit=cover`（在 viewport meta 的 content 中）；
  - 对 Header/Footer 或 main 使用 `env(safe-area-inset-top)` / `env(safe-area-inset-bottom)` 的 padding，避免内容被遮挡。
- 本项目暂无全屏视频或游戏，可把「安全区」列为**低优先级**，有需要再加。

---

### 3.6 图片与媒体（后续内容多了再细化）

**目标**：小屏下图片自适应、尽量不拖慢首屏。

**建议**：

- 已集成 `@nuxt/image`，后续列表/详情中的图片统一用 `<NuxtImg>` 或 `<NuxtPicture>`，配合 `sizes` 做响应式。
- 移动端可优先考虑：
  - 小图或 WebP；
  - 懒加载（NuxtImg 默认行为）。
- 若有视频，使用 `playsinline` 和移动端友好的播放控件。

---

### 3.7 交互与性能

**建议**：

- **触摸**：避免依赖 `hover` 完成关键操作；若有「悬停显示」的菜单，在移动端改为「点击切换」。
- **Loading**：可考虑在根布局加入 `<NuxtLoadingIndicator />`，页面切换时移动端网络较慢时体验更好。
- **避免 300ms 延迟**：Nuxt/Vue 现代栈一般已无此问题，若将来引入其他库导致点击迟钝，再排查。

## 四、Tailwind 断点使用建议

| 断点  | 宽度     | 建议用途                             |
| ----- | -------- | ------------------------------------ |
| 默认  | < 640px  | 手机竖屏，导航抽屉、单列、小字号     |
| `sm:` | ≥ 640px  | 大屏手机/小平板，可略放宽排版        |
| `md:` | ≥ 768px  | 平板竖屏或小笔记本，可切换为桌面导航 |
| `lg:` | ≥ 1024px | 桌面布局，当前 max-w-5xl 已适用      |
| `xl:` | ≥ 1280px | 大屏桌面，保持现状即可               |

**建议**：导航栏「桌面 / 移动」切换点选在 `md`（768px），与常见后台和官网习惯一致。

---

## 五、测试建议

- **真机**：在 iOS Safari、Android Chrome 上各测一种，重点看导航展开/收起、语言切换、各页面跳转。
- **Chrome DevTools**：用设备模拟（iPhone SE、iPhone 12、Pixel 5 等）做快速回归。
- **内容**：
  - 中文长标题 + 英文长标题各测一次；
  - 若有列表或卡片，检查小屏下单列是否正常换行、无横向滚动。
- **性能**：Lighthouse 移动端模式跑一次，关注 LCP、CLS、可点击区域大小。

---

## 六、实施顺序建议

1. **Phase 1（必做）**
   - 实现 AppHeader 移动端：汉堡按钮 + 抽屉导航 + 语言切换。
   - 确认各页面在小屏无横向滚动、标题和正文可读。

2. **Phase 2（建议）**
   - 标题与主内容区做响应式字号与间距（如 `text-2xl sm:text-3xl md:text-4xl`）。
   - 在根布局加入 `<NuxtLoadingIndicator />`。

3. **Phase 3（按需）**
   - 安全区（safe-area-inset）适配；
   - 图片/列表页的响应式与懒加载；
   - Lighthouse 优化与少量 E2E（如：打开首页 → 点汉堡 → 点关于我们）。

## 八、一套代码 vs 新写一套移动端代码

### 8.1 两种思路对比

| 维度         | 一套代码（响应式/自适应）                            | 新写一套移动端代码                                    |
| ------------ | ---------------------------------------------------- | ----------------------------------------------------- |
| **形态**     | 同一项目内用断点/条件渲染区分桌面与移动              | 同项目内移动专用组件/布局，或独立子站（如 m.xxx.com） |
| **维护**     | 一套逻辑、一套路由、一套 i18n/API，改一处两边生效    | 两套（或部分重复）逻辑，改功能要改两处，易不同步      |
| **SEO**      | 同一域名、同一 URL，搜索引擎一份索引                 | 若独立子域需处理 canonical/跳转，否则易重复收录       |
| **首屏体积** | 可通过懒加载、按需加载控制，移动端也能只加载必要部分 | 可做到移动端 bundle 更小，但需拆分构建与部署          |
| **开发成本** | 主要在现有组件上加断点或分支，成本低                 | 新写组件/页面/路由，或新仓库，成本高                  |
| **适用场景** | 官网、后台、内容站，桌面与移动功能一致               | 移动端功能/信息架构与桌面差异很大，或强性能/包体要求  |

### 8.2 「新写一套」的几种做法

1. **同一仓库内：移动端专用组件 + 条件渲染**
   - 例如：`AppHeader.vue`（桌面） + `AppHeaderMobile.vue`（移动），在布局里用 `v-if` / 媒体查询或 `useMediaQuery` 二选一渲染。
   - **可行**：是，逻辑仍在同一项目，i18n/API 共用。
   - **代价**：两套组件要一起改功能，容易漏改一边。

2. **同一仓库内：移动端专用路由（如 /m/ 或 /mobile/）**
   - 例如：`/` 为桌面版，`/m/` 或通过 UA 跳转到移动专用页面。
   - **可行**：是，但需处理：默认入口跳转逻辑、SEO（canonical、hreflang）、书签/分享链接一致性。
   - **代价**：路由与页面数量翻倍，i18n/接口虽可复用，但页面结构要维护两套。

3. **独立项目或子域（如 m.example.com）**
   - 单独一个 Nuxt（或其它）项目，只做移动端，接口共用。
   - **可行**：是，适合移动端与桌面**产品形态差异很大**（如桌面是复杂后台、移动是精简 App 壳）的场景。
   - **代价**：两套部署、两套 CI、两套需求与排期，官网类项目通常不划算。

### 8.3 对本官网项目的建议

- **结论：新写一套代码在技术上可行，但对当前官网场景一般不推荐。**
  - 当前只有首页、新闻、关于我们，桌面与移动**功能一致、信息结构一致**，用一套代码 + 响应式（如 MOBILE-PLAN 前文）即可覆盖，维护成本最低。
- **若坚持「新写一套」**，更现实的是做法 1：
  - 在同一仓库内增加**移动端专用组件**（如 `AppHeaderMobile.vue`、`DefaultLayoutMobile.vue`），在布局里按断点或 `useMediaQuery` 切换，**不新开路由、不独立子域**。
  - 这样仍共用路由、i18n、API，只是 UI 两套，便于在个别区块上做较大差异（例如移动端完全不同的导航结构）。
- **不推荐**：为官网单独做 `/m/` 或 m.xxx.com 子站，除非有明确的产品/运营需求（例如移动端是独立活动页、独立产品线）。

### 8.4 何时更适合「新写一套」

- 移动端与桌面的**功能或信息架构差异很大**（例如桌面是完整后台，移动是只看报表的轻量版）。
- 对移动端**包体/首屏性能**有极强要求，且愿意长期维护两套前端。
- 已有**独立移动团队或独立排期**，可以接受双倍前端维护成本。

当前官网若没有上述需求，优先采用**一套代码 + 响应式（含汉堡菜单 + 抽屉）**即可。

## 九、小结

| 优先级 | 内容                                                         |
| ------ | ------------------------------------------------------------ |
| 高     | Header 移动端：汉堡菜单 + 抽屉（导航 + 语言），断点建议 `md` |
| 中     | 主内容与标题的响应式字号与间距；Loading 指示器               |
| 低     | 安全区、图片响应式与懒加载、Lighthouse/E2E                   |

按上述顺序实施，可在不改业务逻辑的前提下，系统性地完成官网移动端适配。若后续有具体组件或页面需要落代码实现，可再基于本文档拆分为具体任务与 PR。

**方案选择**：推荐一套代码响应式；若确需「新写一套」，建议仅在仓库内增加移动端专用组件并按断点切换，不新开子域或独立项目。
